## D-01. 백엔드 위치 — 사이트 저장소 안 `ask-server/` · `제안`

- **선택지**: (a) 이 저장소 안 하위 디렉터리 (b) 별도 저장소 `usetaehwan-ask`
- **고른 것**: (a)
- **이유**: 코퍼스 원본(`app/_data`, `resume.ts`)과 앵커 함수가 이 저장소에 있다. 저장소를 나누면 코퍼스를 복사하거나 서브모듈로 걸어야 하고, 그 순간 사이트 문구와 챗봇 근거가 어긋날 수 있다. Railway는 root directory를, Vercel은 무시 경로를 지정하면 서로 간섭하지 않는다.
- **대가**: "모노레포 안 함" 원칙(`app/CLAUDE.md`)에서 한 발 벗어난다. 단, 워크스페이스 도구 없이 디렉터리 하나만 추가한다.
- **다시 볼 조건**: 백엔드가 이 사이트 말고 다른 소비처를 갖게 될 때.

## D-02. 오케스트레이션 — LangGraph `StateGraph` · `제안`

- **선택지**: (a) 평범한 함수 파이프라인 (b) LangGraph (c) LangChain LCEL 체인
- **고른 것**: (b)
- **이유**: 이 흐름에는 분기 3개(거절 / 근거 없음 / 생성)와 **검증 실패 시 되돌아가는 루프**가 있다. 함수로 짜면 분기와 재시도 횟수가 if문 속에 숨는데, 그래프로 짜면 간선으로 드러나고 그림이 곧 코드가 된다. 노드 단위로 가짜 LLM을 주입해 테스트하기 쉽고, `stream_mode="updates"`가 노드 완료 이벤트를 주므로 SSE의 단계 이벤트(§8.1)와 그대로 맞물린다. LCEL은 선형 체인에 강하지만 루프와 조건 분기 표현이 어색하다.
- **대가**: 의존성이 하나 는다. 흐름이 단순해서 (a)로도 충분하다는 반론이 가능하다. 그렇게 물으면 "분기·루프·노드 이벤트 세 가지가 필요해서 골랐고, 셋 중 하나만 필요했으면 함수로 짰다"고 답한다.

## D-03. LLM 호출 — Anthropic 공식 SDK 직접 사용 · `제안`

- **선택지**: (a) `anthropic` SDK (b) `langchain-anthropic`의 `ChatAnthropic`
- **고른 것**: (a). LangGraph 노드 안에서 SDK를 부른다.
- **이유**: 비용 지표에 `usage`(입력·출력·캐시 토큰)가 그대로 필요하다. 구조화 출력, `stop_reason == "refusal"`, effort·thinking 설정 같은 최신 파라미터를 래퍼가 따라오길 기다리지 않아도 된다. LangGraph는 LangChain 채팅 모델을 요구하지 않는다.
- **대가**: 모델 교체(예: Gemini 비교)가 래퍼보다 번거롭다. 그래서 `llm.py`에 얇은 프로토콜을 둔다.

## D-04. 벡터 저장소 접근 — SQL 직접 (psycopg + pgvector) · `제안`

- **선택지**: (a) `langchain-postgres`의 `PGVector` / `PGVectorStore` (b) SQL 직접
- **고른 것**: (b)
- **이유**:
  1. 스키마를 직접 정해야 한다. 문서 해시·청크 해시·앵커·**모델별 임베딩 테이블**(D-12 비교용)은 범용 컬렉션 + JSONB 메타데이터 구조에 끼우면 오히려 우회 코드가 는다.
  2. 검색 쿼리가 한 줄(`order by embedding <=> $q limit k`)이다. 추상화가 줄여 줄 코드가 거의 없다.
  3. 면접에서 "VectorDB를 썼다"의 실체가 **쿼리·인덱스 판단(D-09)·해시 기반 증분 갱신**이어야 설명할 거리가 생긴다. 라이브러리 호출 한 줄이면 설명할 게 없다.
  4. 나중에 하이브리드(D-15)를 붙일 때 SQL 쪽이 RRF 결합을 직접 쓰기 쉽다.
- **대가**: 리트리버 인터페이스, 메타데이터 필터 같은 LangChain 생태계 기능을 못 쓴다. 이번 범위에서는 필요가 없다.

## D-05. TS 콘텐츠를 Python으로 — Node 익스포터 → JSON · `제안`

- **선택지**: (a) Python 정규식으로 `.ts` 파싱 (b) Node 스크립트가 모듈을 import해 JSON 출력 (c) Next.js가 빌드 시 JSON 라우트로 공개
- **고른 것**: (b) `npx tsx scripts/ask-corpus.ts`를 `python -m ask.ingest`가 subprocess로 부른다.
- **이유**: (a)는 템플릿 문자열·이스케이프·`getProject()` 같은 계산값에서 깨진다. (c)는 인제스트가 실행 중인 사이트에 의존하게 되고, 필터 전 원문이 공개 JSON으로 노출된다. Node 24의 타입 제거만으로는 `resume.ts`의 확장자 없는 import가 깨져서 `tsx`를 dev 의존성으로 쓴다.
- **대가**: 인제스트에 Node가 필요하다. 로컬과 CI에는 원래 있다.

## D-06. 코퍼스 범위 — "공개 URL이 있는 원본"만 · `확정 2026-10-12`

- **선택지**: (a) 레포 안 md·ts 전부 (b) 사이트에 렌더되는 원본만 (+ 사용자가 고른 외부 글)
- **고른 것**: (b). `projects` · `experience` · `ai-practices` · `talks` · `profile` · `resume.ts`
- **이유**: 출처 `[n]`은 클릭하면 원문으로 가야 하는데, 렌더되지 않는 md는 갈 곳이 없다. 초안과 후보 문구(`resume-v2-candidates.md`)를 넣으면 **고르지 않은 문장이 사실처럼 인용된다**. `resume-pdf-draft.md`는 `resume.ts`와 내용이 같아서, 둘 다 넣으면 top-k를 중복이 차지한다.
- **대가**: 레포 md에만 있고 사이트에 없는 사실은 챗봇이 "모른다"고 한다. 의도한 동작이다.
- **확정 내용**: 티스토리 블로그는 MVP에서 뺀다(레포 안의 AI 노트·발표가 글 역할). `/resume`(noindex)은 출처 링크로 노출해도 된다. 이메일은 사이트에 공개돼 있으니 연락처 질문에는 이메일을 직접 답한다.

## D-07. 앵커 — 페이지와 익스포터가 같은 함수로 만든다 · `확정 2026-10-12 (일부 변경)`

- **선택지**: (a) 익스포터가 앵커 규칙을 따로 구현 (b) `app/_site/anchors.ts` 하나를 페이지와 익스포터가 함께 import
- **고른 것**: (b)
- **이유**: 앵커 문자열이 두 곳에서 만들어지면 언젠가 어긋나고, 그때 깨진 링크는 아무 에러 없이 페이지 맨 위로만 간다. 각(Gak)의 "조용한 실패" 교훈과 같다.
- **변경 2026-10-12 — 의미 키 → 위치 키**: 설계 때는 제목에서 만든 의미 키를 제안했다. 그런데 한글 제목 슬러그는 길고, 제목을 다듬을 때마다 링크가 깨진다. 그래서 `case-1`, `feature-2` 같은 위치 키로 바꿨다. 순서를 바꾸면 앵커가 달라지지만, 페이지와 코퍼스가 같은 함수를 쓰므로 다시 인제스트하면 맞춰진다. 어긋날 수 있는 것은 "인제스트 전의 운영 DB"뿐이고, CI의 corpus 잡이 사이트 문구가 바뀔 때마다 코퍼스를 다시 뽑는다.

## D-08. 청크 — 레코드 단위 (고정 길이 아님) · `제안`

- **선택지**: (a) 고정 길이 + 겹침 (b) 마크다운 헤더 기준 (c) 원본 레코드(사례·항목·경력) 단위
- **고른 것**: (c). 1,200자를 넘으면 문장 경계에서 나눈다. md 소스를 추가하면 (b)를 쓴다.
- **이유**: 원본이 이미 "문제·파악·해결" 같은 의미 단위로 구조화돼 있다. 고정 길이로 자르면 "문제"와 "해결"이 다른 청크로 갈라져, 한쪽만 검색되면 반쪽 답이 나온다. 청크마다 **경로 머리말**(프로젝트 › 각 › 사례: …)을 붙여 짧은 청크도 문맥을 잃지 않게 한다.
- **메타데이터**: `doc_id` · `section` · `anchor` · `url` · `breadcrumb` · `source_path` · `chunk_hash`
- **검증**: hit@k로 확인한다. 낮으면 머리말 유무를 먼저 비교한다.

## D-09. 벡터 인덱스 — 두지 않는다 (전체 스캔) · `제안`

- **선택지**: (a) HNSW (b) IVFFlat (c) 인덱스 없음
- **고른 것**: (c)
- **이유**: 청크가 수백 개 이하다. 전체 스캔은 **정확한** top-k를 주고, 이 규모에서는 근사 인덱스가 아낄 시간이 거의 없다. 근사 인덱스는 이득 없이 recall 손실 가능성만 더한다. 인덱스가 없으니 `vector` 차원을 고정하지 않아도 되고, 그래서 서로 다른 차원의 임베딩 모델을 한 테이블에서 비교할 수 있다(D-12).
- **다시 볼 조건**: 청크 1만 개 이상이거나, 검색 단계 p95가 응답 시간의 10%를 넘을 때. 그때는 모델별 고정 차원 컬럼 + HNSW로 간다.

## D-10. 인용 검증 — 런타임은 결정적 규칙, 의미 검증은 평가에서 · `제안`

- **선택지**: (a) 런타임에도 LLM이 "이 인용이 문장을 뒷받침하나" 심사 (b) 런타임은 코드 규칙(번호 범위·누락·숫자 대조·형식), 의미 심사는 오프라인 평가
- **고른 것**: (b)
- **이유**: 런타임 LLM 심사는 호출 수·지연·비용을 늘리고, 심사 자체가 또 검증해야 할 LLM 출력이 된다. 이력 챗봇에서 가장 해로운 환각은 **숫자**인데, 숫자는 코드로 대조할 수 있다. 오늘어디의 "번호로만 출처를 돌려받는다"에 각(Gak)의 "숫자는 서버가 만든다"를 더한 규칙이다. 의미 수준의 뒷받침은 평가에서 다른 모델(Sonnet 5.5)이 심사하고, 사람 표본 검수로 심사 자체의 일치율도 함께 보고한다.
- **fallback도 코드**: 재생성까지 실패하면 **검증을 통과한 문장만** 남긴다. 마지막 안전장치를 다시 LLM에 맡기지 않는다.

## D-11. 생성 모델 — Claude Haiku 5.5 · `제안`

- **선택지**: Haiku 5.5 ($0.10/$0.50 per 1M) · Sonnet 5.5 ($2/$10) · Gemini 무료 등급
- **고른 것**: Haiku 5.5. 분류·판정·생성 모두에 쓰고, 평가 심사에만 Sonnet 5.5를 쓴다.
- **이유**: 일이 "주어진 근거 안에서 요약하고 인용하기"라서 큰 모델의 추론력이 크게 필요하지 않다. 품질은 검증 레이어가 하한을 잡는다. 질문당 비용 추정은 약 $0.0012다(design §6). 생성 모델과 심사 모델을 다르게 둬서 자기 답을 자기가 채점하지 않게 한다. Gemini 무료 등급은 오늘어디에서 써봤지만, 무료 등급 입력이 제품 개선에 쓰일 수 있어서 방문자 질문을 보내는 용도로는 뺐다.
- **다시 볼 조건**: 평가에서 인용 정확도나 잘못된 거절률이 기준 미달이고, 프롬프트·thinking 조정으로도 안 오를 때 Sonnet 5.5로 같은 질문셋을 돌려 비교한다.

## D-12. 임베딩 — voyage-4-lite 기본, gemini-embedding-001과 실측 비교 · `제안` → 결과: eval-report

- **후보**: Voyage `voyage-4-lite`($0.02/1M, 200M 무료) · Google `gemini-embedding-001`($0.15/1M, 무료 등급) · `BAAI/bge-m3`(자체 호스팅). 제외: OpenAI `text-embedding-3-small`(무료 분량 없음, 한국어 근거 약함)
- **고른 것**: voyage-4-lite를 기본으로 두고, D2~3에 gemini-embedding-001과 **같은 질문셋의 hit@5**로 비교해 확정한다. bge-m3는 시간이 남으면 로컬에서만 비교한다.
- **이유**: 코퍼스가 작아서 어떤 후보든 비용 차이는 0에 가깝다. 그러니 가격이 아니라 **내 질문에서의 검색 품질**로 골라야 한다. 벤치마크 순위는 내 코퍼스의 성능을 보장하지 않는다. bge-m3는 한국어 근거가 가장 좋지만, 약 2.3GB 모델을 Railway 컨테이너에 올리면 메모리·이미지·콜드스타트 비용이 생겨서 배포 후보에서 뺐다.

## D-13. 대화 — 싱글턴 · `제안`

- **선택지**: (a) 멀티턴 (이전 대화를 근거로 질의 재작성) (b) 질문마다 독립
- **고른 것**: (b)
- **이유**: 평가가 결정적이 되고, 인젝션이 이전 턴에 숨을 자리가 없고, 비용이 예측 가능하다. 대가로 "그거 테스트는 몇 개야?" 같은 후속 질문은 못 푼다. 패널에서 "질문은 하나씩 독립적으로 답해요"라고 안내한다.

## D-14. 프록시 — Next.js Route Handler (rewrites 아님) · `제안`

- **선택지**: (a) `next.config` rewrites (Orbit 방식) (b) `app/api/ask/route.ts` Route Handler (c) 브라우저 → Railway 직접 + CORS
- **고른 것**: (b)
- **이유**: Orbit에서 rewrites를 쓴 이유는 **쿠키**(iOS Safari ITP)였다. 이번에는 쿠키가 없고, 필요한 건 ① 공유 비밀 헤더를 붙여 Railway 직접 호출(레이트리밋 우회)을 막는 것과 ② Vercel이 확인한 클라이언트 IP를 넘기는 것이다. `next.config`의 rewrites 설정만으로는 업스트림 요청에 비밀 헤더를 붙일 수 없다. 미들웨어로 붙일 수는 있지만, 그러면 사이트 전체 요청 경로에 코드가 끼어든다. Route Handler는 이 경로 하나에만 작동하고, 입력 길이 검사와 에러 변환도 같은 곳에 둘 수 있다. (c)는 비밀을 브라우저에 둘 수 없어 ①이 불가능하다.
- **대가**: Vercel 함수 실행 시간 안에서 SSE를 그대로 흘려야 한다. 응답은 수 초 수준이라 여유가 있지만, 배포 후 실측으로 확인한다.

## D-15. 키워드 하이브리드 — 처음엔 안 넣고 평가로 결정 · `제안`

- **선택지**: (a) 처음부터 벡터 + Postgres FTS (b) 벡터만 → 고유명사 누락이 측정되면 글자 bigram BM25 + RRF
- **고른 것**: (b)
- **이유**: Postgres 기본 FTS 설정에는 한국어 형태소 분석이 없다. "결제를"과 "결제"가 다른 토큰이 된다. 코퍼스가 작아 BM25는 앱 메모리에서 충분하다. 넣을지는 hit@k에서 고유명사 질문이 실제로 떨어지는지를 보고 정한다. 이것이 "개선 1회"의 1순위 후보다.

## D-22. Gemini 무료 등급 429 — 인제스트만 기다렸다 재시도 · `확정 2026-10-17`

- **발견**: 첫 실제 인제스트(123청크)가 세 번째 배치에서 429로 멈췄다. 무료 등급 한도는 모델당 분당 100건이고, `batchEmbedContents`는 배치 안의 **항목 하나하나를 1건으로** 센다. 50개짜리 배치 두 번이면 한도가 찬다. 1건짜리 호출의 응답 형태(768차원)는 정상이었다.
- **선택지**: (a) 배치를 줄인다 — 항목 단위로 세므로 효과가 없다 (b) 429가 오면 응답의 `RetryInfo.retryDelay`만큼 기다렸다 같은 배치를 다시 보낸다 (c) 결제를 켜서 한도를 올린다
- **고른 것**: (b)를 코드에 넣고, 배포 전에 (c)도 한다. 재시도는 **문서 임베딩(인제스트)에만** 최대 3회, 대기 상한 65초로 둔다. 질의 임베딩은 방문자 요청 안에서 돌기 때문에 기다리지 않고 바로 실패한다.
- **이유**: 결제를 켜도 한도 자체는 남는다. 인제스트는 오프라인 배치라 1분을 기다려도 괜찮다. 반면 방문자가 20초씩 멈춰 있는 것보다는 빨리 실패하는 편이 낫다.
- **함께 정한 것**: 무료 등급은 입력 데이터를 Google이 제품 개선에 쓸 수 있는 약관이다. 코퍼스는 공개 내용이라 괜찮지만, 운영에서는 방문자 질문도 임베딩하려고 보낸다. 그래서 **배포 전 AI Studio 결제 활성화를 필수 항목**으로 둔다.

## D-27. 운영 모드에서 비밀이 없으면 서버를 시작하지 않는다 · `확정 2026-10-17`

- **발견**: 배포 체크리스트를 쓰다가 조용히 실패하는 설정 두 개를 찾았다. `ASK_PROXY_SECRET`이 비어 있으면 프록시 검사(D-14)를 건너뛰어 백엔드가 누구에게나 열린다. `ASK_IP_HASH_SECRET`이 빠지면 저장소에 공개된 기본값 `dev-only-secret`으로 IP를 해시한다(D-19). 비밀이 공개돼 있으면 IPv4 전체를 대입해 해시에서 IP를 되찾을 수 있다. 둘 다 서버는 정상으로 뜨고 헬스체크도 통과한다.
- **선택지**: (a) 문서 경고만 (b) 시작할 때 경고 로그만 남기고 계속 뜬다 (c) 운영 모드에서는 시작을 거부한다
- **고른 것**: (c). `app_factory`가 앱을 만들기 전에 검사한다. 문제가 있으면 빠진 항목과 고치는 방법을 `CRITICAL` 로그로 찍고 종료 코드 1로 끝난다. traceback은 찍지 않는다. 처음에는 예외를 그대로 올렸는데, 메시지가 uvicorn 내부 traceback 40줄 밑에 묻혔다.
- **운영/개발 구분**: Railway가 모든 배포에 넣는 `RAILWAY_ENVIRONMENT_ID`가 있으면 운영이다. 아니면 `ASK_ENV=production`일 때만 운영이고, 나머지는 개발이다. `ASK_ENV`에 모르는 값이 들어오면 시작을 거부한다.
- **이유**: 표시 변수(`ASK_ENV=production`)에만 기대면, 그걸 깜빡했을 때 검사도 함께 꺼져 처음 문제와 똑같아진다. 플랫폼이 자동으로 넣는 값을 기준으로 삼으면 사람이 빠뜨릴 수 없다. 같은 이유로 Railway 위에서는 `ASK_ENV=development`로 검사를 끌 수 없게 했다. 실패 쪽으로 기우는 편(fail-closed)이 안전하다. 로컬에서는 키를 넣고 서버를 띄워도(오늘처럼) 개발 모드라 지금 그대로 동작한다.
- **대가**: 운영 배포가 비밀 설정 실수로 실패할 수 있다. 하지만 Railway에서는 실패한 배포가 트래픽을 받지 않고 이전 배포가 남으므로, 열린 채로 뜨는 것보다 낫다.
- **검증**: 모드 판별 6가지, 비밀 조합 5가지, `app_factory`가 앱을 만들기 전에 멈추는지, 실제 `uvicorn --factory` 프로세스가 traceback 없이 메시지를 찍고 0이 아닌 코드로 끝나는지를 테스트한다. 로컬 개발 서버는 `mode=development`로 뜨는 것을 확인했다.

## D-29. "자료에 없음" 문장 허용 범위 확장 — 런타임 검증 규칙 변경 · `확정 2026-10-17`

- **발견**: v1의 q19(Redis, 답 없는 질문)에서 생성 모델은 "제공된 자료에는 Redis 캐시를 설계한 경험에 대한 내용은 없습니다"라고 정직하게 썼다. 그런데 `NO_INFO` 정규식이 "자료에" 바로 뒤의 "없"만 받아서 이 문장이 `uncited`로 걸렸다. 재생성에서도 같은 일이 생겼고, salvage가 이 문장을 지우고 캐시 문장만 남겨 "Redis 경험이 있는 것처럼" 읽히는 답이 나갔다. q14에서는 "제공된 자료에 정보가 없습니다"가 같은 이유로 걸렸다.
- **선택지**: (a) 생성 프롬프트로 정해진 문구만 쓰게 한다 (b) 정규식을 "자료/출처/근거 + 에(는)/에서(는) … 없습니다·않습니다·못했습니다" 꼴로 넓히고, 영어도 "the sources do not mention…" 꼴을 더한다
- **고른 것**: (b). 단, "자료에 따르면 … 없습니다", "출처에서 보듯 …" 같은 **자료를 근거로 한 사실 주장은 제외**해 여전히 인용을 요구한다.
- **이유**: 정해진 문구를 강제해도 모델은 조금씩 다르게 쓴다. 이 규칙의 목적은 "자료에 없다고 말하는 문장"을 허용하는 것이지, 특정 문자열을 허용하는 게 아니다. 반대 방향 위험(인용 없는 사실 주장이 빠져나가는 것)은 부정문 사실 주장 5개를 테스트로 고정해 막았다.
- **범위**: 측정 수정이라고 불렀지만, 실제 서비스의 검증 동작(어떤 답이 나가는가)도 바뀐다. 이 정규식은 평가의 "근거 없음으로 답했나" 판정에도 같이 쓰인다.
- **검증**: v1에서 걸린 실제 문장 6개는 이제 통과하고, 부정문 사실 주장 5개는 여전히 `uncited`로 걸린다. 테스트를 먼저 써서 6개가 실패하는 것을 확인한 뒤 정규식을 고쳤다.
- **변경(2026-10-17, v2 후)**: 평가 코드의 "근거 없음으로 답했나" 판정이 이 정규식을 **답 전체**에 대고 있었다. 그래서 문장 끝 조건(`$`) 때문에 v2 q19를 놓쳤다. 런타임 검증과 같은 단위(문장)로 찾도록 평가를 고쳤다. 런타임 동작은 처음부터 문장 단위라 바뀐 것이 없다.

## D-31. 검색 설정 — 하한 0.55 채택, k 8 유지 · `확정 2026-10-17`

- **실험**: v2와 다른 조건은 그대로 두고 `ASK_TOP_K` 8 → 15, `ASK_MIN_SCORE` 0.15 → 0.55만 바꿨다(tuned-gemini). 그다음 조정에 쓰지 않은 holdout 8문항을 tuned 설정으로 한 번 돌렸다.
- **결과**: 답 없는 질문 5/5 유지(판정이 거름). 여러 근거 질문에서 기대 출처가 근거에 들어온 비율 0.80 → 0.90. 인용 정확도(심사) 98.1% → 85.7%. holdout은 8/8, 인용 18/18.
- **해석**: 하한 0.55는 Gemini 점수 분포(0.51~0.82)에서 바닥선일 뿐이고 결과를 거의 바꾸지 않았다. k 15는 여러 근거 질문의 범위를 넓히지만, 근거가 늘수록 생성이 근거를 묶은 문장을 쓰고 그 인용이 어긋난다. 정확도 하락 7건은 아직 사람이 검수하지 않았다.
- **선택지**: (a) 하한 0.55만 채택하고 k는 8 유지 (b) 둘 다 채택 (c) k 15와 함께 생성 프롬프트를 고쳐(사실마다 그 사실이 있는 근거를 인용, 근거에 없는 "~뿐/두 개" 같은 범위 단정·비교 금지) 다시 잰다
- **고른 것**: (a). 하한 기본값은 임베더별로 둔다(`MIN_SCORE_DEFAULTS`: gemini 0.55, hash 0.15). voyage는 아직 재지 않아 0.15다. `ASK_MIN_SCORE`를 넣으면 그 값이 우선한다.
- **이유**: 이 챗봇의 핵심 약속은 인용 정확성이다. 여러 근거 질문에서 프로젝트를 하나 빠뜨리는 것보다, 틀린 근거를 인용하는 쪽이 더 해롭다고 봤다. 하한을 한 값으로 바꾸지 않은 이유는, 해시 임베더(오프라인 모드)의 점수가 0.55에 거의 닿지 않아 오프라인 그래프가 늘 "근거 없음"이 되기 때문이다.
- **미룬 것**: 생성 프롬프트 수정(c)과 새 holdout. holdout은 tuned 설정으로 이미 한 번 썼으므로, 채택한 (a)는 holdout으로 확인되지 않은 상태다.
- **주의**: holdout은 tuned 설정으로 이미 한 번 썼다. (a)나 (c)를 고르면 그 최종 설정은 holdout으로 확인되지 않은 상태다. 엄밀히 확인하려면 새 holdout이 필요하다.

- **고른 것**: (b). 항목마다 `item`(이름) · `match`(정규식 목록, 대소문자 무시) · `sources`(그 항목을 뒷받침하는 근거)를 둔다. 지표는 두 개다.
  - **답의 항목 재현율** — 전체 기대 항목 중 답에 언급된 비율. 검색에서 빠진 항목도 실패로 센다.
  - **근거에 든 항목 → 답에 언급** — 그 항목의 근거가 판정을 통과한 경우만 센다. 생성이 빠뜨린 것만 남는다(h08 유형).
  - 답하지 못했으면 언급하지 않은 것으로 센다. `--rescore <run.json>`으로 저장된 실행을 다시 잴 수 있다.
- **이유**: 항목 이름은 답에 거의 그대로 나온다(프로젝트명·서비스명). 문자열로 찾으면 결정적이고 비용이 없으며, 심사 모델의 판정 흔들림(D-25)을 들이지 않는다. (c)는 문서 단위라 같은 문서의 다른 청크로 맞아 버리고(v1 q14), 인용하지 않고 이름만 말한 경우를 놓친다. 지표를 둘로 나눈 것은 원인(검색 / 생성)을 가르려는 것이다.
- **기대 항목을 정한 방법**: Neon 코퍼스 123청크 본문을 읽고, 질문에 대한 답이 분명한 항목만 넣었다. q12에서 끼니는 넣지 않았다 — 끼니 페이지의 검증은 에이전트가 지적하는 방식이고(`project:kkini#case-2`), 코드로 검증한 것은 에이전트 보고의 숫자를 grep으로 다시 센 일(`ai:agent-team#case-4`)이라 "LLM 결과를 코드로 검증"인지 애매하다. 한국어 '각'은 "각각·생각·각 페이지"에 걸리지 않게 뒤에 오는 글자를 제한한 정규식을 쓰고, 테스트로 고정했다.
- **한계**: 범위 단정("두 프로젝트에 있습니다", "…'오늘어디'입니다")은 이 지표가 직접 세지 않는다. 항목을 빠뜨리지 않으면 단정이 틀리지 않게 되는 쪽으로만 간접 반영된다. 단정 자체는 생성 프롬프트(D-36)로 다룬다. 기대 항목은 같은 사람(Claude)이 정했으므로 사람 검수가 필요하다. holdout.yaml의 기대 항목은 holdout-tuned 실행 **후에** 더했다.
- **기존 실행 재채점**: 30문항 v1·v2 81.8%(9/11), tuned 100%(11/11) — v1·v2의 누락 2건(q12 오늘어디, q14 각)은 모두 근거에 없던 항목이라 "근거에 든 항목 → 답에 언급"은 9/9다. holdout-tuned는 75%(3/4), 근거에 든 항목 3/4 — h08 쪽쪽을 잡는다.
